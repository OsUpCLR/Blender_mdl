# SC Model IEX — изменения

## 0.3.2 (2026-10-25)

Ориентация по соглашению осей, LOD по спеке, сборка деталей, цвет стекла.

### Добавлено

* `axes="auto"` + `_auto_forward`: «перед» по костям — двигатели/выхлопы на game +Z
  (Blender -Y), курсовые пушки на game -Z; при обратном — поворот 180° вокруг вертикали;
* `rotate_selected` — визуальный поворот (-/+90° по X и Z, 180° по Y) с записью обратной
  матрицы; при экспорте поворот отменяется (`export_new.py`);
* `_place_part_at_bone` — деталь ставится в rest-матрицу кости-крепежа;
* `_spread_parts` — деталь размножается по всем точкам крепления категории (`boost_1..N`);
* `model.check_counts` — валидатор пакета: `parts`/`materials` из `+0x38` против файлов и
  блоков `.mdf`, FVF (`+0x04`) против страйда (`+0x08`);
* `model.lod_groups` по спеке: `lod[k]` в `+0x20` — последняя деталь уровня (включительно),
  уровни вложенные, детали после `lod[0]` — attachments;
* стекло в `obj_pipeline`: блок `dyn_glass` с `UserParam0_Float4` (спектр),
  `UserParam0_Float` (прозрачность/глянец) и `UserParam1_Float4` (альбедо);
* лог дублируется в `%TEMP%/SC_MODEL_IEX_log.txt`;
* понятная ошибка для пака без моделей; повторная распаковка при пустом кэше.

### Документация

* `docs/OBJ_TO_GAME.md` — импорт OBJ в игру;
* `docs/CUSTOM_ENGINE_EFFECTS.md` — кастомный двигатель и эффекты;
* `docs/SHIP_GLASS.md` — стекло: отдельный меш, `dyn_glass`, цвет в `.mdf`.

### Проверено

* `check_counts` проходит на `race3_l_t1`, `race4_l_phoenix`;
* LOD: `race3_l_t1` (8,6,3,0) -> [9,7,4]; `race4_l_phoenix` -> [10,9,6]; `r1_h_t1` -> [10,9,5];
* `r2_m_evilmask`: `boost` размножен на 3 точки (12 объектов), посажен на `boost_1/2/3`;
* smoke: импорт `r2_m_evilmask` (27 мешей, 1 арматура), `obj_to_msh`, `dds_to_tfh` — OK.

## 0.3.1 (2026-10-25)

Импорт сторонних моделей (OBJ) и текстур (DDS), исправления экспорта.

### Добавлено

* оператор `obj_to_msh` — OBJ -> `.mdl-msh###` + `.mdl-hdr` (разбивка по материалам,
  индекс материала в `+0x00` меша, шаблон формата вершин);
* оператор `dds_to_tfh` — DDS -> `.tfh/.tfd` (DXT1/3/5 и несжатые, мипы, флаг куба);
* оператор `obj_to_game` — полный конвейер: масштаб, материалы `ship_hull` с полным
  набором сэмплеров, текстуры DXT5, `.mdf`, `.mdl-hdr`, скелет/анимации из шаблона,
  сборка `.pak`;
* `sc_tools/obj_pipeline.py` (конвейер), `sc_tools/dxt_encode.py` (энкодер DXT);
* `export_sc` копирует `.mdl-skl` и `*.anim` из шаблона, если арматуры нет.

### Исправлено

* `msh.py`: поле `+0x18` пишется как `n_idx` (раньше бралось из шаблона — новые меши
  не читались движком); поддержан индекс материала в `+0x00`;
* `hdrwrite.py`: при одном LOD `+0x20` и `+0x28` пишутся нулями (иначе модель
  не рисуется);
* `model_write.py`: для корабельных паттернов автоматически добавляются `UserParam2`
  и `pins`; из путей сэмплеров срезаются расширения `.tfh/.tfd`;
* `export_new.py`: `import struct`; индекс материала из свойства `sc_material_index`.

### Проверено

* конвертация OBJ (4 090 вершин / 5 042 грани, 2 материала) в пак 184 КБ — модель
  грузится в игре, текстуры на месте;
* DDS 1024x1024 -> `.tfh` (1 544 Б) + `.tfd` (1 396 736 Б), таблица уровней совпадает
  с эталонной парой игры.

## 0.3.0 (2026-10-23)

Слияние двух линий: стабильная `0.2.4` (правка существующей модели) и
экспортная линия 22.10 (`SC_MODEL_IEX_NEW`).

### Добавлено (экспорт «с нуля», 22.10)

* `sc_tools/sklwrite.py` — писатель `.mdl-skl` (`build_skl`, `make_bone`),
  проверен: 3 837 файлов байт-в-байт в raw-режиме;
* `sc_tools/hdrwrite.py` — пересборка `.mdl-hdr`: bbox + LOD (4×u16 @0x20);
* `sc_tools/model_write.py` — `.model` + `.skins`;
* `sc_tools/mdp_write.py` — разбор/сборка `.mdp` (тело-меш, v0x0C/0x0D);
* `sc_tools/export_new.py`, `sc_tools/blend_export.py` — Blender → игра;
* `sc_tools/msh.py` дополнен `build_block`/`build_mesh` (любая топология);
* операторы: `export_mesh_new`, `export_skeleton`, `export_animation`,
  `export_hdr`, `export_model_file`, `export_mdp`.

### TPAK: приведено к проверенным данным

* сжатие — уровень 9 (было 6: пак выходил больше оригинала на 1,7–4,6 %);
* чанкование `.tfd`: каждый уровень режется на `ceil(size / 1,5 МиБ)` с
  делением по строкам, число уровней берётся из `a` (у кубов `6 × mips`).
  Было `round(base / 1 392 640)` только для последнего чанка — расходилось
  с игрой у 247 из 10 113 текстур (72 пака). Сейчас 0 расхождений;
* таблица `index` — всегда `argsort` имён (как во всех 588 паках игры);
* имена пишутся в cp1251 (кириллица в пути больше не роняет сборку);
* корневой `pak.py`: уровень 9, убран лишний префикс `\x00\x00` в старом
  `pack_dir`, `index` — argsort.

### Тип 2 (коробка) и несколько тел для compound_model (24.10)

* в окне экспорта коллизии появился тип **«Коробка (2)»** — одно тело по
  габаритам выделенных объектов (`half` в `+0x40`, центр в `pos`);
* галочка **«Тело на объект»** — для `compound_model`: отдельная выпуклая
  оболочка (тип 6) на каждый выделенный объект (в игре >1 тела обязательны);
* исправлена сборка нескольких тел: смещение каждого шейпа (`offset`) теперь
  проставляется при компоновке `.mdp`, иначе парсер видел шейп за пределами файла;
* проверено: куб → тип 2 (half 1,1,1); два куба с галочкой → 2 тела типа 6.

### Textures from game paks (24.10, build 53)

* textures are searched in the game `.pak` files directly: a pak is ranked by
  the texture path (`models_ships_race_4_l...`), its name table is decoded and
  only the needed `.tfh`/`.tfd` are extracted to the cache;
* no `sc_index.json` and no unpacked folder are required for import — with empty
  settings Phoenix imported with 15 textures, 0 "texture not found" messages;
* per-run caches: pak name tables, found and missing textures (repeated
  lookups are instant);
* `unpacked_root` is now an optional preference (kept for legacy layouts);
  documentation no longer mentions machine-specific paths.

### Portable paths (24.10, build 52)

* game data folder is auto-detected on any PC: `STARCONFLICT_DATA`/`SC_DATA`
  env var, Steam install path from the registry (`SteamPath`), then all
  libraries from `steamapps/libraryfolders.vdf`; the two hardcoded
  `C:\Program Files...` paths remain only as the last fallback;
* unpacked paks folder: preferences or `SC_UNPACKED`/`SC_UNPACKED_ROOT` env;
  the old hardcoded `the game .pak files` guess is removed;
* FAQ/UI texts no longer mention machine-specific paths.

### Bilingual FAQ and language-aware UI (24.10, build 51)

* FAQ text block now contains both languages: English section followed by the
  Russian one (plus import/export sections in both);
* UI labels follow the Blender interface language: when the Blender UI is
  Russian, property names, descriptions, operator labels and enum item labels
  are shown in Russian (`sc_tools/i18n_ui.py` + `_L()`), otherwise English;
* translation is resolved when the add-on is loaded, so a Blender restart is
  needed after changing the interface language.

### English UI and FAQ (24.10, build 50)

* the add-on UI is fully translated to English: property names/descriptions,

### Шейдерная UV-анимация отключена (24.10, сб.48)

* `animated_mock` больше не анимируется: убраны keyframes на `Mapping`

* скелетные анимации не затронуты.

* действия из `.anim` теперь называются ровно как файлы

* поза — `pose_<имя>`;
* префикс убран и в пак-импорте, и при импорте из папки; экспорт `.anim`
  по-прежнему понимает старые имена с префиксом.

* имя файла не показатель: `cap_anim` анимирует `cap_anim_jnt*`, которые
  живут в скелете **корпуса**, а у капсулятора свой риг с `cap_rot_anim_jnt`;

* проверено: Phoenix — `cap_anim` (1..49, 12 костей `cap_anim_jnt`) на корпусе,

### Анимации по своим арматурам (24.10, сб.43)

* все `.anim` раньше вешались на одну (основную) арматуру — из-за этого
  анимация капсулятора крутила корпус и «ломала» скелет;
* теперь анимация выбирает арматуру по токену в имени: `capacitor/cap` → своя,
  `eng` → двигатель, `drone/turret` → своя, иначе пропуск; остальные — корпус;
* активное действие корпуса выбирается только из его собственных анимаций;
* проверено на Phoenix: капсулятор крутится на своём риге, корпус не искажается.

### animated_mock: прозрачный слой (24.10, сб.42)

* детали `msh003`/`msh004` Phoenix — не самостоятельная поверхность, а
  светящиеся полосы поверх корпуса: Base Color чёрный, **Alpha = маска**,
  Emission = скролл ×12 (сила 4), смешивание BLENDED;
* до этого деталь была непрозрачной и «закрывала» корпус — выглядела как
  поглотитель света;
* проверено рендером: корпус виден сквозь деталь, поверх — красные полосы.

### animated_mock: вид без «намасленности» (24.10, сб.40)

* Base Color = скролл-текстура (×2.5), без маски;
* Emission = скролл × маска (×4);
* Roughness = 1, Specular = 0, Metallic = 0 — убран «масляный» блик,
  из-за которого детали `msh003`/`msh004` выглядели однотонными;
* проверено на Phoenix: на деталях виден рисунок и красное свечение.

### Текстуры: animated_mock и дефолтная покраска (24.10, сб.39)

* `dyn_animated_mock` (детали с бегущей текстурой): Base Color = `ColormapSampler`
  (скролл) × маска `DiffuseSampler`, Emission = тот же сокет, прокрутка V
  по `UserParam0[0]` (ключи на 1 и 250 кадрах). Раньше в Base Color попадала
  маска, а скролл игнорировался — детали `msh003/msh004` Phoenix были чёрными;
* дефолтная покраска: если деф по имени модели не найден, ищем
  `Def.<name>.model="...<base>"` в `ship.lua` (пример: `race4_l_phoenix`
  принадлежит `Ship_Race1_L_T3_Pirate`) и берём `default_custom_elements`;
  без этого не накладывались красные акценты;
* проверено на Phoenix: hull 0.83, детали с прокруткой и красные акценты
  выглядят как в игре.

### Формула корабельной оболочки (24.10)

### Тип 7: итог (24.10, сб.38)

* синтез типа 7 работает в игре: контейнер `TCF` с таблицей чанков **типа 9**,

### Тип 7: BVH расшифрован, синтез заработал (24.10)

* BVH шейпа типа 7: заголовок **0xC0** (bbox, масштабы квантования, магия 282,
  число узлов `+0x44`, флаг 16-байтовых узлов `+0x48`, count2 `+0xB4`), затем
  узлы по 16 Б: 6×u16 квантованный AABB (min xyz, max xyz) + int32-ссылка;
* ссылка: `>= 0` — лист (индекс треугольника), `< 0` — внутренний узел,
  `-end` (конец поддерева); обход префиксный, левый ребёнок `i+1`;
* после индексов обязателен **паддинг** до 4 двуслов (`(-3·nt) & 3`) — иначе
  движок считает размер неверным;
* **контейнер `.mdp` обязателен от оригинала** (doff, tail, gap с таблицей имён,
  trailer, hash): собранный «с нуля» контейнер движок отвергает;
* AABB узлов считаются по вершинам поддерева (не по центрам треугольников);
* лимит: в игре максимум **224** треугольника; при >256 сервер физики падает
  (проверено 512/1609/6886), поэтому в экспорте `max_tris = 224` и равномерная
  децимация по сетке;
* проверено в игре: 100 и 224 треугольника — коллизия работает; 6886 — сервер
  падает.

### Тип 7: проверка в игре — BVH обязателен (24.10)

Игровой тест (обломок фрейтера `freighter_imper_wreck` в «Транспортном узле
Империи», `.mdp` заменён на синтезированный тип 7 с нулевым BVH):

* **коллизия полностью отключилась** — объект пролетается насквозь;
* вывод: движок **не строит BVH из вершин/индексов**, хвост обязателен;
* поэтому синтез типа 7 без BVH не годится; в экспорте опция «Тримеш (7)»
  помечена как экспериментальная и предупреждает об этом;
* правки в `Test_SC` откачены (бэкапы `E:\WorkspaceDSH\_backup_models`).

### `.mdp` тип 7 (тримеш) — разобран (24.10)

* заголовок шейпа типа 7: `+0xD0` — число треугольников, `+0xDC` — число
  вершин; вершины с `+0xF0` по `vec4` (шаг 16), сразу за ними `nt*3` u32
  индексов (`0xFFFFFFFD` — restart); дальше BVH;
* `parse_mdp` декодирует вершины и треугольники (`tris_idx`), bbox для типа 7
  считается по вершинам;
* `import_mdp` для типа 7 строит **готовый меш** (вершины + грани), для типа 6 —
  оболочку, для типа 2 — коробку;
* проверка модели показывает «вершин / треугольников / коробок»;
* round-trip `.mdp` не изменился: **1613/1613** байт-в-байт.

Проверено: 582 шейпа типа 7 в `models` (15 658 треугольников), 0 ошибок
декодирования; `crystal_mineral_03` — 20 вершин / 36 граней и 15 / 26;
`platform_04` — 52 вершины / 100 граней.

### Единое окно экспорта и режимы импорта (24.10)

* `File → Export → Star Conflict…` — одно окно с галочками: меши + `.mdl-hdr`,
  `.model/.skins`, коллизия, скелет, анимации, `.mdf`, сборка `.pak`, авто-LOD;
  что отмечено — то и пишется (проверено: `.model`/`.mdp`/`.mdf` — байт-в-байт,
  `.pak` собирается);
* `File → Import → Star Conflict…` — один диалог с галочками **«Модель»** и
  **«Анимации»**: только модель, только анимации (на активную арматуру) или всё
  вместе; `.pak` определяется по расширению, «Вся папка» — батч;
* убран пункт «Разворот вращения деталей» из импорта (и из импорта из пака);
  отдельного пункта меню для анимаций больше нет.

### `.mdp`: таблица имён и масштаб коллизии (24.10)

Из игрового теста (Hercules ×10) выяснилось главное:

### `.mdp`: правильная раскладка и настоящая оболочка (24.10)

По обновлённому `_analysis/MDP_PHYSICS.md` и проверке на файлах:

* тело — **0x4C** (а не 0x60 с именем внутри); шейп лежит по
  `data_base + 0x10 + body[+0x44]`, `data_base = 16 + dataOffset`;
* версия **0x0C** (заголовок 0x14, тела с 0x34) поддержана наравне с 0x0D;
* тип 6 — **вершины** (count × vec4 с +0x50), а не плоскости; тип 2 — коробка
  (half extents во float на +0x40), тип 7 — тримеш (сохраняется сырыми байтами);
* `import_mdp` строит **выпуклую оболочку** из вершин (bmesh convex_hull);
  для типа 2/неполных данных — куб по AABB; по объекту на тело;
* `build_from_mesh` пишет уникальные вершины (раньше писал плоскости — для новых
  моделей это было неверно); `build_mdp` возвращает исходные байты, если тела не
  правили, и сохраняет сырые шейпы остальных типов.

Проверено: **1613/1613** `.mdp` в `models` разбираются и проходят round-trip
байт-в-байт; sniper — оболочка 20 вершин / 36 граней (bbox вершин 6.01 × 9.37 ×
2.09, в заголовке на 0.04 больше с каждой стороны — как в игре); 6-теловый
`life_part2.mdp` — 6 объектов; коробка `defaultpolygon.mdp` — 114 × 114 × 0.34.

### Импорт `.mdp` (23.10)

### Батч-экспорт (23.10)

* новый модальный оператор **«SC: экспорт моделей из сцены (прогресс/Esc)»**

### Прогресс и отмена (23.10)

* проверка версии сравнивается с **проверенной** 5.2: предупреждение только
  если Blender ниже неё (раньше порог был 4.2);
* прогресс-бар у импорта модели (по мешам через `on_mesh`) и у экспорта мешей
  (по объектам); значения в `_Progress` защищены от исключений;
* новый оператор **«SC: импорт моделей из папки (прогресс/Esc)»**
  (`import_batch`): модальный, по одной модели за тик, прогресс по числу
  моделей, **Esc отменяет** оставшиеся (импортированное остаётся, в отчёте —
  сколько успело); ошибки отдельных моделей не прерывают батч.

Проверено (headless, `modal()` вызывался вручную): полный батч папки sniper —

### Валидация и round-trip (23.10)

* новый модуль `sc_tools/validate.py` (без bpy): `check_model(base)` проверяет
  заголовок, `mesh_count` против файлов, границы LOD, число порогов, `.mdf`
  (число материалов), `.mdl-skl`, `.mdp`, `.anim` (длительности/каналы) и пары
  `.tfh/.tfd`; `roundtrip(source, out_dir, out_base, kinds=…)` сравнивает
  экспорт с источником;
* операторы **«SC: проверить модель (отчёт)»** и **«SC: проверить round-trip»**
  в меню; отчёты пишутся в `SC_MODEL_IEX_report.txt` / `SC_MODEL_IEX_roundtrip.txt`
  (если папка источника недоступна на запись — в `%TEMP%`);
* у экспорта мешей появилась галочка **«Проверять после экспорта»** (по
  умолчанию вкл.): сверяются `.mdl-hdr` и меши, результат добавляется в
  сообщение оператора;
* при регистрации аддон проверяет версию Blender и предупреждает, если она
  ниже 4.2 (проверен на 5.2);
* проверка только того, что экспортировали: если экспортирован один LOD,
  меньшее число мешей не считается ошибкой (в отчёте — «в источнике N»).

Проверено: `sniper` — 17 OK / 0 warn / 0 err; `phoenix` — 57 OK; отсутствующая
модель — 1 err без падения. В Blender: операторы доступны, авто-проверка после
экспорта пишет «проверка: OK 4, WARN 4» (расходятся только заголовки частей,
что ожидаемо при экспорте одного LOD).

### Текстуры из DDS, галочка LOD и ручная раскладка (23.10)

* `texture.dds_to_pair()` и оператор **«SC: .tfh/.tfd из .dds»**: DXT1/3/5 и
  несжатые (A8, L8, A8L8, 32/24/16 бит), с мип-цепочкой; код формата `idx`
  подбирается по fourCC (DXT1→11, DXT3→13, DXT5→10) или задаётся вручную;
  проверка: DDS → tfh/tfd → DDS даёт **тот же файл** (картинка 1:1), `.tfd`
  совпадает с исходным побайтно; `.tfh` может отличаться паддингом между
  таблицей и данными (у игры он 0–12 байт и не критичен: смещения в таблице);
* у экспорта мешей появилась **галочка «Генерировать LOD»** (+ число уровней
  0–4); при выключенной авто-LOD экспорт пишет только то, что размечено вручную;
* ручная раскладка: оператор **«SC: назначить LOD выделенным»** (`assign_lod`)
  ставит `sc_lod` выбранным мешам; экспорт сортирует по LOD-мажору и пишет
  границы в `.mdl-hdr`;
* операторы добавлены в меню панели.

Проверено: ручная раскладка (2 меша в LOD0, 2 в LOD1) → hdr старты `[0,2]`;
галочка авто-LOD (2 уровня) → 3 файла `.mdl-msh`; `back.dds` (DXT5 64×64) →
`mytex.tfh` 1484 Б + `.tfd` 4096 Б, читается как DXT5/7 мипов.

### Полный цикл «с нуля» (23.10)

Новую модель теперь можно собрать без донора:

* **формат вершин по умолчанию** — `msh.default_template()`: stride 32
  (f20: позиция, нормаль, тангенс, UV, UV2) или 36 со скелетом (f21);
  поле «Шаблон .mdl-msh» у `export_mesh_new` стало необязательным;
* **авто-LOD** — свойство «Авто-LOD уровней» (0–4): из LOD0 модификатором
  Decimate генерируются уровни 1…N (ratios 0.5/0.25/0.12/0.06), имена и
  `sc_lod` расставляются автоматически;
* **`.mdf` из материалов Blender** — новый оператор `export_mdf`
  (`model_write.build_mdf`): по одному `material` на материал, сэмплеры
  угадываются по суффиксу картинки (`_d`, `_nm`, `_s1`, `_glow`, `_sc`, `_pdo`);
  если ничего не выбрано — берутся все меши сцены;
* **`.mdl-hdr`** подхватывает `material_count` из лежащего рядом `.mdf`, а
  `export_hdr` получил поле «LOD: размеры групп» (например `4,4,1,1`);
* порядок для новой модели: материалы → `.mdf` → меши (+LOD) → `.mdl-hdr`
  (создаётся вместе с мешами) → `.mdl-skl`/`.anim` → `.model`/`.skins`.

Проверено на сфере с нуля: 3 LOD (482/242/122 вершины, stride 36), `.mdl-hdr`
(мешей 3, материалов 1, LOD 1+1+1), `.mdf` (DiffuseSampler), `.mdp` 19
треугольников, `.mdl-skl` 2 кости, `.model`/`.skins`; всё упаковано
`tpak.build_dir` в `starship.pak` (9 файлов) и прочитано обратно.

### Нормали при правке и модель «с нуля» (23.10)

* сохранённые нормали (`sc_normals`) пишутся, только если вершины не двигали;
  при правке геометрии они **пересчитываются** по Blender (v.normal, smooth);
  свойство оператора «Сохранять исходные нормали» (`keep_normals`) возвращает
  старое поведение;
* смена топологии (другое число вершин) — нормали считаются заново всегда;
* новая модель без исходника: `.model` больше не тащит действия из сцены —
  берутся только привязанные к её арматуре;
* проверено: модель-сфера с нуля даёт полный набор — `.mdl-msh000` (формат из
  шаблона-донора), `.mdl-hdr` (мешей 1, bbox по вершинам), `.mdp` (16
  треугольников по формуле), `.model`/`.skins`, `.mdl-skl`.

Что нужно для новой модели: донорский `.mdl-msh` как шаблон формата, арматура
для скелета, действия для анимаций, `.mdf` (не пишется плагином) и упаковка в
`.pak` отдельным инструментом.

### Корабли: сырые позиции/кости и общие части (23.10)

* при импорте сохраняются `sc_pos_raw` (позиции как в файле, до сдвига детали)
  и `sc_bone_index` (индекс кости как в файле); экспорт возвращает их побитово,
  если вершины не двигали — иначе считается как раньше;
* общие части класса (`r4_l_eng` и подобные) больше не переименовываются в
  `<новая база>_<имя>`: они подключаются в игре по исходному имени, поэтому
  пишутся как есть; части самой модели (`<корабль>_boost` и т.п.) — от новой базы;
* исправлено затенение индекса объекта в цикле проверки позиций (`i` → `k`):
  из-за него имена файлов становились `.mdl-msh<число вершин>` и часть мешей
  перезаписывалась.

Проверено: `race4_l_phoenix` — 22/22 меша во всех четырёх базах байт-в-байт
(включая общий `r4_l_eng`); `race1_l_t5_sniper` — 21/21; `ship_event_aprile` —
20/20; `.model` и `.mdp` — байт-в-байт.

`.mdl-geo`/`.mdl-dfm` к кораблям не относятся: в корпусе 174 `.mdl-geo`, все в
`mapskit` (геометрия уровней), у моделей кораблей их нет.

### `.model`/`.skins` при переименовании (23.10)

* шаблон `.model` теперь используется и при смене имени базы: имя меняется
  только в код-полях (`mesh`, `skin`, `physics`, `#include`, имена `.anim`),
  комментарии остаются как были (`model_write.rename_base`, по границе слова —
  без «renamed_renamed_…»);
* `.skins` копируется с заменой имени базы;
* `.mdp` копируется и при переименовании (содержимое от имени не зависит);
* найден и исправлен дефект: экспорт `.model` брал **все** действия из
  `bpy.data.actions`, включая анимации ранее импортированной модели — теперь
  фильтр по арматуре и имени базы (в одной сцене несколько кораблей больше не
  смешиваются).

Проверено: sniper и `ship_event_aprile` — при том же base `.model`/`.mdp`
байт-в-байт; при переименовании `.model` совпадает с переименованным шаблоном
(0 лишних `anim`-блоков), `.mdp` копируется.

### Приближённая формула `.mdp` (23.10)

Если исходного `.mdp` нет (новая модель, чужая геометрия):

1. берётся **LOD0** (самый подробный — он всегда полный; грубые LOD у части
   моделей частичные, у lunokhod LOD3 — лишь фрагмент);
2. строится выпуклая оболочка (`bmesh.ops.convex_hull` + триангуляция);
3. оболочка ужимается модификатором **Decimate (collapse)** до `target_tris`
   (по умолчанию **16** — медиана по 968 файлам игры: 25 % — 12, 75 % — 34);
4. AABB и плоскости треугольников пишутся в `.mdp`.

Проверено: lunokhod — 15 треугольников / 496 Б (в игре файла нет),
sniper — 15 против 20 у игры, `ship_event_aprile` — 15 против 8; AABB
совпадает с `.mdl-hdr`.

Попутно исправлено: координаты `.mdp` брались прямым преобразованием
`(-x, -z, y)` вместо обратного `(-x, z, -y)` — сгенерированные файлы были
повёрнуты относительно модели (3 места в операторе).

Авторскую оболочку игры (8–20 плоскостей) формула не воспроизводит — это
ручная/генераторная заготовка; при наличии исходного `.mdp` он по-прежнему
копируется байт-в-байт.

### Ревизия кода 23.10: найденные дефекты

* `unchanged` не был определён после переделки на `unchanged_by_src` — hdr не
  собирался ни для одной базы (ошибка `name 'unchanged' is not defined`);
* `g_pos`/`g_nrm` прибавляли `+0.0`, что стирало знак у `-0.0` (lunokhod,
  `_cap`: расхождения в младшем байте z);
* единичная `matrix_world` применялась к вершинам и нормалям: `1*x + 0*y + …`
  превращает `-0.0` в `+0.0` — теперь единичная матрица пропускается;
* `patch_model` не видел имена `.anim` внутри блоков `files { … }` и дописывал
  дубли (event_aprile: 781 → 879 Б);
* `.model` без арматуры теперь берёт базу из `sc_src_msh` (импорт без скелета).

Проверено после правок: sniper (21 меш, 4 базы), `ship_event_aprile`
(20 мешей, 5 LOD), `lunokhod` (5 мешей, 5 LOD) — меши, `.mdl-hdr`, `.model`
и `.mdp` совпадают с источником байт-в-байт (у lunokhod `.mdp` в игре нет —
строится оболочка).

### Авторский bbox и оболочка `.mdp` (23.10)

* если у объектов не менялось число вершин, габарит в `.mdl-hdr` берётся из
  шаблона (`keep_template_bbox`): у части моделей он авторский и меньше
  геометрии (lunokhod), теперь круг даёт **0 отличий** и там;
* `.mdp` для новой геометрии строится как **выпуклая оболочка** (bmesh
  convex_hull + триангуляция): sniper — 318 треугольников вместо 21 273;
  в игре коллизия тоже упрощённая (у sniper 20 треугольников на 21 тыс.
  вершин), но авторской оболочки у нас нет — своя ближе по смыслу;
* свойство оператора `hull` (по умолчанию вкл.) отключает оболочку.

### `.model`, `.skins`, `.mdp`: сохраняем исходное (23.10)

* `.model` больше не собирается с нуля: берётся исходный текст (комментарии,
  порядок токенов, незнакомые поля) и дописываются только недостающие
  `anim`-блоки (`model_write.patch_model`); префикс `SC_MODEL_IEX_` у действий
  снимается, имя `.anim` не дублирует базу;
* `.skins` копируется из источника, если он есть;
* `.mdp` копируется как есть, если модель не менялась: в нём выпуклая оболочка
  (десятки треугольников), а не вся геометрия — пересборка из мешей давала
  340 КБ вместо 576 Б; при `max_tris > 0` по-прежнему строится заново;
* проверено на `sniper`: `.model` 1055 Б и `.mdp` 576 Б — байт-в-байт.

### Пороги при росте числа LOD

* если в шаблоне нет порогов вообще — первый берётся как `(r * 118.9)^2`
  (медиана `sqrt(порог)/радиус` по 1263 моделям);
* недостающие достраиваются множителем 0.16 в квадратах (медиана отношения
  соседних порогов в дистанциях — 0.4).

### LOD: пороги, части, lodsBounds (23.10, продолжение)

* пороги считаются по формуле парсера игры: `stored = pi * (r * 1505.88 /
  sqrt(d))^2`, поэтому при изменении габарита `d` масштабируется как
  `(r_new / r_old)^2` (константы из `game.exe`: 1280.0, 1.17647, pi, 0.5);
* при росте числа LOD недостающие пороги достраиваются прогрессией 0.25 от
  последнего (эмпирика; при смене числа уровней это эвристика);
* `lodsBounds` из `.model` (до 3 факторов) читается `model_def.parse_model_def`
  — движок берёт пороги оттуда, `+0x28` в заголовке справочный;
* экспорт разводит части (`_boost`, `_cap`, `_eng`) по своим базам: у каждой
  свой `.mdl-hdr` и `.mdf`; сдвиг детали на позицию кости снимается при экспорте
  (`sc_model_iex_offset`), иначе деталь уезжала бы на кость дважды;
* проверено на `race1_l_t5_sniper`: 21 меш, 4 базы — **все меши байт-в-байт**,
  заголовки с правильными LOD-границами.

### LOD: границы из заголовка, 5 уровней (23.10)

* `+0x20` — 4×u16 внутренних стартов LOD (по убыванию, добитые нулями);
  проверено на 3046/3046 моделях. `lod_groups()` больше не гадает по материалам;
* импорт: `lod=-1` грузит все уровни, каждый меш получает `sc_lod` и коллекцию
  `LOD<n>`;
* экспорт: LOD-мажорный порядок, формат вершин — из исходного меша (`sc_src_msh`),
  размеры групп уходят в `+0x20`, пороги — из шаблона (до 4, включая `+0x34`);
* проверено: sniper (10 мешей, 4 LOD) — 10/10 байт-в-байт, hdr −1 байт (bbox);
  `ship_event_aprile` (20 мешей, 5 LOD) — **20/20 мешей и hdr байт-в-байт**.

### `.mdl-hdr` переписан по проверенной раскладке (23.10)

* `sc_tools/hdrwrite.py`: `parse` / `build` / `validate`; на корпусе 4 376
  заголовков `build(parse(x)) == x` — 4 376/4 376;
* пишется `+0x38 = (material_count << 16) | mesh_count` — по нему движок
  решает, сколько мешей грузить. Раньше он не писался: при другом числе
  мешей движок читал столько же, сколько в шаблоне, и меши терялись;
* `+0x20` больше не затирается «индексами LOD» (это доп. параметр) —
  сохраняется из шаблона;
* `material_count` берётся из `.mdf` (у оператора `export_hdr` новое поле
  «.mdf (необязательно)»), иначе — из шаблона;
* bbox по-прежнему считается по вершинам мешей.

### Исправлен круг импорт → экспорт

* оси: экспорт применял то же преобразование M, что и импорт; теперь M⁻¹ —
  вершины, нормали и тангенсы возвращаются в систему игры;
* UV: V переворачивается обратно (включая второй набор — lightmap/AO);
* обход граней: разворачивается только если импорт разворачивал (флаг
  `sc_winding_reversed` в меше);
* нормали и тангенсы (включая знак бинормали) сохраняются атрибутами
  `sc_normals` / `sc_tangent` / `sc_tangent_w` — Blender 5.2 кастомные
  нормали не принимает;
* индекс кости в вершине пишется «номер − 1», как в файлах игры;
* скелет: позиция и поворот кости — относительно родителя, исходные
  кватернионы/матрицы/флаги сохраняются в арматуре (`sc_bone_quats`,
  `sc_bone_raw`, `sc_flags`) и возвращаются для неизменённых костей.

Проверено на `race1_l_t5_sniper` (Blender 5.2 headless): экспорт без правок
даёт `.mdl-msh000` **1 537 700 Б байт-в-байт** и `.mdl-skl` **10 784 Б
байт-в-байт**.

Почему скелет раньше не сходился (и как исправлено):

* ключ кости назывался `quat`, а `sklwrite.build_skl` читает `rotation` —
  в файл уходил единичный кватернион вместо файлового;
* кватернионы в игре содержат `-0.0` и `w = 0.99999994`, а не ровно `1.0`:
  любое преобразование через double (нормализация, математика) съедает и
  знак нуля, и младшие разряды;
* неизвестные 28 байт в записи кости (0x24…0x3F) и байты позиции тоже
  не восстанавливались из float.

Теперь в арматуре (`sc_bone_raw`) лежат **сырые байты** кости — `pad`
(28 Б), `position_raw` (12 Б), `quat_raw` (16 Б), — и `build_skl` пишет их
как есть (а не пересобирает из float). Для новых/изменённых костей работает
обычный путь через позицию и кватернион.

### Осталось

* `.mdp` собирается заново из треугольников (сборка восстанавливает только
  однотельные; многотельные — до 881 тела — пока нет);
* `.mdl-hdr` строится по экспортированным мешам: если сложить в одну базу все
  части корабля, bbox и LOD будут от всей модели (в тесте — 8 мешей), а не от
  одной; для отдельной базы LOD/bbox считаются по её мешам;
* UV2/тангенсы сохраняются атрибутами; если меш перестроен в Blender так, что
  вершин стало другое число, экспорт берёт значения Blender;
* `.model`/`.skins` собираются заново по скелету и действиям (в тесте 209 Б
  против 1055 Б оригинала — исходные комментарии/поля шаблона не переносятся).
